# Пайплайны

[Оглавление](README.md) | [English version](../en/pipelines.md)

Devicelab предоставляет сценарные объекты, а не элементы GStreamer. Библиотека
владеет медиаграфом, workers, ограниченными очередями, временными метками,
разрешением устройств и остановкой. Объекты GStreamer и PipeWire остаются
деталями реализации.

## Громкость

Каждый pipeline принимает `volume: float = 1.0`, имеет свойство `volume` и
метод `set_volume(value)`. Используется линейный gain: `0.0` означает тишину,
`1.0` не меняет сигнал, `10.0` является максимальным поддерживаемым gain.
Значение можно задать до `start()` или изменить в работающем pipeline; во время
startup, stopping или после stop возникает `PipelineStateError`. Элемент gain
стоит после PCM-нормализации и до всех downstream-веток, поэтому handler,
динамик и WAV/FLAC-запись получают измененный сигнал. Gain выше `1.0` может
вызвать clipping S16LE. Recovery микрофона сохраняет и повторно применяет
последнее значение.

## Общий жизненный цикл

Каждый пайплайн одноразовый:

```text
created -> starting -> running -> stopping -> stopped
```

`start()` строит граф, переводит его в `PLAYING`, запускает мониторинг и delivery
workers и ожидает готовности сценария. Захват с микрофона и файла также ожидает
согласования выходных caps и запуска handler. Для запуска speaker не нужна
предварительная передача PCM; фактическое downstream-согласование может
произойти при первом `submit()`.

Bus watcher наблюдает предупреждения, ошибки, состояния и EOS. Предупреждения
логируются, но не являются терминальными. Исключения workers и bus errors
становятся наблюдаемыми ошибками пайплайна и разблокируют ожидающие операции.

Корректная остановка устанавливает границу приема, передает EOS и завершает
принятую работу. Немедленная остановка напрямую сигнализирует отмену. Оба пути
закрывают доступ к графу, переводят GStreamer в `NULL` и ограниченно ожидают
workers библиотеки.

Отдельного состояния failed нет. Завершение всегда приводит к `stopped`, а
`failure` отличает неуспешный результат. Первая терминальная ошибка остается
основной; последующие ошибки очистки или callbacks доступны в
`secondary_errors`.

## Захват с микрофона

Без явного выбора каналов и записи граф имеет вид:

```text
PipeWire source
  -> audio conversion
  -> resampling
  -> точные caps S16LE/rate/channels
  -> линейная громкость
  -> ограниченная 200 ms очередь DROP_OLD
  -> app sink с отбрасыванием и емкостью один буфер
  -> Python delivery worker
```

При `ChannelSelection` перед нормализацией добавляются caps точного числа
входных каналов и их mapping. При записи нормализованный звук проходит tee:

```text
normalized audio -> tee
  -> ограниченная DROP_OLD live-ветка -> app sink -> handler
  -> ограниченная 1000 ms BLOCK-ветка -> WAV/FLAC encoder -> временный файл
```

Live-ветка сохраняет более свежий звук, если handler отстает. Ветка записи
сохраняет полноту и может создать обратное давление для всего графа.

### Доставка данных

App sink отображает каждый корректный sample и копирует его в little-endian
`int16`. Delivery worker получает ограниченную группу доступных пакетов и
объединяет только непрерывные пакеты. Неограниченного предварительного чтения на
стороне Python нет.

Новый публичный chunk начинается при признаке разрыва от графа, принудительной
границе или расхождении timestamp более чем на период одного выходного кадра.
Округление в пределах одного кадра допускается. Некорректный пакет отбрасывается
и заставляет следующий chunk иметь `discontinuity=True`.

### Автоматическое восстановление

Автоматически перезапускается только микрофон. Во время работы восстановимы:

- ошибка, отправленная текущим элементом `pipewiresrc`;
- неожиданный EOS;
- несовместимые capture caps;
- третья ошибка mapping буфера в скользящем окне десять секунд;
- вторая ошибка некорректного кадра или отсутствующего времени в их общем
  скользящем окне десять секунд.

События возрастом ровно десять секунд уже исключаются. Допускаются три попытки
замены после задержек 0,25, 1 и 4 секунды. Успешная замена не восстанавливает
бюджет сразу: он сбрасывается, если новое восстановление началось не менее чем
после 60 секунд стабильной работы.

Во время восстановления публичное состояние остается `running`. Остановка
отменяет backoff. После успешной замены увеличивается generation, заново
калибруется время, `on_restart()` вызывается до новых данных, а первый chunk
помечается разрывом. Ошибки handler, записи, инвариантов графа, детерминированной
конфигурации, bus errors не от source и исчерпание попыток терминальны.

## Захват из файла

WAV использует `wavparse`, FLAC - `flacparse` и `flacdec`. Далее оба проходят
общую нормализацию:

```text
file source -> parser/decoder -> conversion -> resampling -> точные S16LE caps -> линейная громкость
```

`FileReplayMode.REALTIME` добавляет синхронизацию по часам и ограниченную
доставку `DROP_OLD`. Источник ведет себя как работающий в реальном времени и
может отбросить старый звук при медленном handler.

`FileReplayMode.AS_FAST_AS_POSSIBLE` не ограничивает скорость часами и использует
ограниченную блокирующую доставку. Все корректные кадры выдаются со скоростью,
которую поддерживает handler. Относительные media timestamps одинаковы в обоих
режимах, но wall-clock anchors различаются. В быстром режиме `captured_at_ns` -
логическое время медиа, которое может опережать фактическое время обработки.

Естественный EOS завершает принятые пакеты и считается успехом. Ошибки parsing,
caps, mapping, кадров и timestamps терминальны. Файловый пайплайн не
восстанавливается и не поддерживает ветку записи.

## Воспроизведение на динамик

Без записи граф имеет вид:

```text
Python S16LE array
  -> bounded app source
  -> audio conversion
  -> resampling
  -> точные caps S16LE/rate/channels
  -> линейная громкость
  -> PipeWire sink
```

`submit()` делит вход на GStreamer-буферы длительностью не более 20 ms, но в
буфере должен быть хотя бы один кадр, поэтому эта граница действует при частоте
от 50 Hz. Staging в AppSrc рассчитан на 250 ms PCM после целочисленного
округления числа байтов и блокирует вызывающий поток при заполнении. На крайне
низких частотах рассчитанная емкость может стать нулевой, что GStreamer трактует
как отсутствие ограничения; такая конфигурация не входит в гарантию
ограниченной буферизации playback. Принятый при нормальной работе звук намеренно
не отбрасывается ради снижения задержки.

PTS выбирается как более позднее из конца предыдущего успешно отправленного
буфера и текущего pipeline running time. Поэтому звук в очереди остается
непрерывным. Реальный период без вызовов `submit()` создает разрыв времени;
Devicelab не вставляет искусственную тишину. Состояние времени изменяется только
после успешной отправки.

При записи нормализованный звук проходит tee:

```text
normalized audio -> tee
  -> ограниченная 250 ms BLOCK-ветка -> PipeWire sink
  -> ограниченная 1000 ms BLOCK-ветка -> WAV/FLAC encoder -> временный файл
```

Корректная остановка разделяет operation boundary с `submit()`: она ожидает уже
принятый полный вызов, отклоняет последующие, отправляет EOS, завершает
воспроизведение и публикует запись. Немедленная остановка не ожидает эту границу
и может прервать отправку или отбросить staged audio.

`submit()` возвращается после принятия массива AppSrc, а не после физического
воспроизведения. У speaker playback нет естественной границы завершения:
`wait()` требует остановки из другого потока либо терминальной ошибки.

## Публикация записи

Сначала данные пишутся в скрытый временный файл, принадлежащий пайплайну. Цель
атомарно публикуется только после encoder EOS. Без overwrite публикация не может
заменить файл, появившийся конкурентно; с overwrite цель атомарно заменяется.

При восстановлении микрофона текущее поколение завершается и открывается
`<stem>.<generation><suffix>`. Проверка коллизий выполняется независимо для
каждого сегмента. Корректное завершение speaker гарантирует наличие в записи
всего успешно принятого PCM. Немедленная остановка или асинхронная ошибка
speaker удаляет неопубликованный временный файл.

Запись speaker содержит только отправленный PCM после регулировки громкости.
Временные промежутки простоя не заполняются тишиной.

## Объединение файла и воспроизведения

Файл можно декодировать и нормализовать через handler, передающий каждый chunk
в speaker:

```python
from lumivox_devicelab import CaptureHandler

class PlaybackHandler(CaptureHandler):
    def __init__(self, speaker):
        self._speaker = speaker

    def on_chunk(self, chunk):
        self._speaker.submit(chunk.samples)
```

Сначала запустите speaker, затем файловый capture и дождитесь его завершения.
После EOS корректно остановите speaker. Обратное давление `submit()` естественно
ограничивает быстрый файловый захват, поскольку обе стороны используют
ограниченные блокирующие пути. При отмене или ошибке немедленно остановите оба
пайплайна и сохраните первую ошибку приложения. Полный пример оркестрации
находится в `examples/record_playback_gui.py`.

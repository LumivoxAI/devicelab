# Элементы управления потоком GStreamer

Этот модуль содержит внутренние обёртки над элементами GStreamer, управляющими буферизацией, ветвлением и синхронизацией потока. Общие инварианты внутреннего GStreamer-слоя описаны в `../README.md`.

## AudioQueue

`AudioQueue` является обёрткой над `queue`. Она отделяет поток выполнения upstream от downstream и ограничивает количество ожидающего аудио только по времени.

```python
AudioQueue(max_time_ms=200, overflow_policy=QueueOverflowPolicy.DROP_OLD)
```

| Аргумент | Значение | Политика |
| --- | --- | --- |
| `max_time_ms` | Положительное целое; по умолчанию `200` | Максимальная длительность данных в очереди. Передаётся в `max-size-time` в наносекундах. |
| `overflow_policy` | `QueueOverflowPolicy`; по умолчанию `DROP_OLD` | Определяет поведение при заполнении очереди. |
| `name` | `str | None` | Необязательное имя GStreamer-элемента. |

| Свойство | Значение обёртки | Политика |
| --- | --- | --- |
| `max-size-time` | `max_time_ms * 1_000_000` | Единственная включённая граница очереди. |
| `max-size-buffers` | `0` | Не ограничивать очередь числом буферов. |
| `max-size-bytes` | `0` | Не ограничивать очередь объёмом байтов. |
| `leaky` | Значение `overflow_policy` | Применять выбранную политику при достижении `max-size-time`. |

`max_time_ms` должен быть положительным; иначе конструктор завершается `ValueError`. Ограничение только по времени делает ёмкость независимой от разбиения потока на GStreamer-буферы. Фактический объём памяти всё равно зависит от negotiated audio caps и размера буферов.

### QueueOverflowPolicy

| Значение | `leaky` | Поведение |
| --- | --- | --- |
| `BLOCK` | `0` | Не отбрасывать данные. Когда очередь заполнена, создать обратное давление на upstream. |
| `DROP_NEW` | `1` | Отбрасывать новый входящий буфер, сохраняя уже ожидающие данные. |
| `DROP_OLD` | `2` | Отбрасывать наиболее старые ожидающие данные, сохраняя актуальное аудио. |

`DROP_OLD` выбран по умолчанию для live-аудио, ориентированного на voice-agent: при медленном downstream доставить недавний звук полезнее, чем продолжать обработку накопившегося устаревшего. Эта политика означает, что downstream может пропускать интервалы потока. Pipeline и клиентский код не должны предполагать непрерывность каждого буфера только потому, что upstream продолжает работать.

`BLOCK` подходит для пути, где важнее полнота данных, например записи файла. Он может увеличить задержку или замедлить связанные ветви pipeline. `DROP_NEW` сохраняет старый backlog и поэтому обычно не подходит для интерактивного capture-пути.

Очередь не заменяет ограничение на границе `AppSink` или `AppSrc`: она задаёт отдельную границу между элементами GStreamer. В capture pipeline bounded leaky-очередь располагается перед `AppSink`. После `Tee` каждая ветвь должна начинаться собственной `AudioQueue`, чтобы медленная ветвь не блокировала остальные.

## Tee

`Tee` является обёрткой над `tee` и разделяет один входной поток на несколько downstream-ветвей. В отличие от обычного `BaseElement.link()`, каждый вызов `Tee.link()` запрашивает новый source pad по шаблону `src_%u` и связывает его со статическим sink pad следующего элемента.

```python
tee = Tee(name="capture_tee")
tee.link(AudioQueue()).link(AppSink(spec))
tee.link(AudioQueue()).link(WavEnc()).link(FileSink("recording.wav"))
```

В примере очереди изолируют ветвь capture delivery и ветвь записи. Без них блокировка одной ветви способна остановить распределение данных через `tee` для другой.

`link()` возвращает `next_element`, поэтому после него можно продолжать обычное построение цепочки. Если шаблон request-pad отсутствует, `tee` не смог выделить source pad, у следующего элемента нет sink pad или связывание pad завершилось неуспешно, метод освобождает уже выделенный pad, когда это необходимо, и выбрасывает `GStreamerElementError`.

Каждый успешно запрошенный source pad хранится обёрткой. Владелец pipeline должен вызвать `release_request_pads()` при teardown, до освобождения `tee`. Метод освобождает все сохранённые request-pad и очищает внутренний список; повторный вызов безопасен. `Tee` не создаёт и не добавляет элементы ветвей в pipeline: builder должен добавить `tee` и все элементы ветвей самостоятельно до запуска pipeline.

## ClockSync

`ClockSync` является обёрткой над `clocksync` для воспроизведения файлов в реальном времени. Он синхронизирует доставку буферов с clock pipeline, используя временные метки потока.

```python
FileSrc("input.wav").link(WavParse()).link(ClockSync())
```

| Свойство | Значение | Политика |
| --- | --- | --- |
| `sync` | `True` | Задерживать буферы до их времени в clock pipeline. |
| `sync-to-first` | `True` | Сопоставлять первый буфер с текущим временем pipeline, чтобы replay начинался сразу, а не ожидал абсолютный PTS файла. |

`ClockSync` нужен builder-у для `FileReplayMode.realtime`: временные метки файла сохраняются, и поток имитирует живой источник. Для `FileReplayMode.as_fast_as_possible` builder не должен добавлять этот элемент, поскольку цель такого режима -- обработать файл с максимально доступной скоростью.

Синхронизация не нормализует аудио, не ограничивает очередь и не гарантирует фиксированную end-to-end задержку. Перед границей Devicelab декодированный файл всё ещё требуется привести через `AudioConvert`, `AudioResample` и `CapsFilter` к `RawAudioSpec`.
